# Архитектура tg-net-bot

## Границы системы

- `cmd/tg-net-bot` — CLI и минимальная точка входа; `serve` запускает бота и монитор, `check` выполняет ручную проверку, `block` обращается к Cheburcheck.
- `internal/telegram` — Telegram Bot API, клавиатуры и пользовательские диалоги. Основные действия доступны кнопками; команды остаются дополнительным интерфейсом.
- `internal/monitor` — доменные действия и периодический обход пользовательских алертов. Зависимости заданы маленькими интерфейсами `Repository`, `NetworkChecker`, `BlockChecker`, `Notifier`.
- `internal/checker` — разовые и периодические проверки ICMP, TCP, HTTP(S). Хостом может быть домен, IPv4 или IPv6.
- `internal/blockcheck` — typed use case базовой и расширенной проверки, общий batch, лимиты и TTL-cache port. Его используют Telegram и CLI.
- `internal/cheburcheck` — HTTP/SSE-адаптер: `Check` вызывает только `/api/v1/check`, `Probe` отдельно читает `/api/v1/probe/{id}`.
- `internal/storage` — SQLite-таблицы `targets` и `alerts`, восстановление активных серверов и алертов после перезапуска.
- `internal/app` — сборка адаптеров и управление временем жизни приложения.

## Потоки

### Навигация Telegram

Главный экран разделяет действия на «Сервисы», «Серверы» и «Алерты». Действия раздела и списки показываются inline-кнопками в одном актуальном сообщении; экраны редактируются на месте и содержат контекстные кнопки назад и домой. Карточки серверов и алертов содержат основные сведения и действия рядом с объектом.

### Ручная проверка

Пользователь выбирает один или несколько сохранённых серверов кнопками (или вводит произвольный IP/домен) → выбирает ICMP/TCP/HTTP(S) и параметры → `monitor.Service.Check` проверяет каждую цель → бот обновляет сообщение о текущем сервере и выводит результат для каждой цели. Сохранение сервера для разовой проверки не требуется. Проверки выполняются последовательно с ограниченным числом одновременных операций; действие «Главное меню» отменяет активную операцию через context.

### Настройка алерта

Пользователь выбирает сервер, метод и собственный интервал в Telegram → `monitor.Service.AddAlert` валидирует настройки → SQLite сохраняет правило. Общего интервала проверок в env нет. Внутренний scheduler часто просыпается, но запуск проверки каждого правила определяется его пользовательским интервалом. Мастер с мультивыбором серверов пока заканчивается экраном обзора: пакетное сохранение и группы отложены до согласования их правил. Существующие одиночные алерты и команды остаются доступными.

### Смена состояния

Первый результат устанавливает исходное состояние. Повторный результат того же состояния не создаёт уведомление. Переход в недоступность вызывает только лёгкий базовый Cheburcheck и уведомляет пользователя с обоими результатами; расширенный probe автоматически не запускается. Переход назад в доступность отправляет уведомление о восстановлении. Последнее состояние сохраняется в SQLite.

### Проверка блокировок и расширенный probe

Одиночная и пакетная проверки используют общий use case. Пакет идёт последовательно с общим per-process ограничителем для всех чатов: 30 check/мин и 5 probe/мин, burst 1 — текущие defaults upstream, настройки production могут отличаться. После каждого ответа интерфейс получает отдельный typed результат. HTTP 429 становится отдельной rate-limit ошибкой; пакет останавливается и оставшиеся цели помечаются как не отправленные.

Базовый результат сохраняется в общем краткоживущем Redis cache вместе с upstream ID. Максимальный локальный срок задаётся `BLOCKCHECK_CACHE_TTL` и по умолчанию равен 24 часам; непроверенный JWT `exp` читается адаптером только как верхняя граница срока cache и probe, не как основание доверия к токену. Если `exp` отсутствует или не распознаётся, применяется безопасный максимум 3 часа. Бот и CLI используют одинаковый Redis keyspace. Кнопка/команда probe использует сохранённый ключ и делает второй HTTP запрос только после явного действия. В подробном результате отображаются реальные SSE events, онлайн-узлы, ответившие и фактические verdict labels; отсутствующие upstream значения не подменяются догадками. Старые строки в SQLite `block_check_cache` автоматически не переносятся и таблица остаётся для совместимости схемы, но новый код её не использует.

## Основные сценарии и доказательства

| Сценарий | Проверка |
| --- | --- |
| Кнопочный пользовательский путь: добавить IPv6 сервер, проверить, настроить и увидеть алерт | `internal/telegram` functional tests с локальным HTTP-моком Bot API |
| Ручные ICMP/TCP/HTTP проверки, доступный/недоступный сервер, IPv4/IPv6 | `internal/checker` unit tests и локальный listener/HTTP server |
| Cheburcheck primary ровно один HTTP запрос, typed поля, 429/Retry-After, ручной SSE probe и исходные verdict labels | `internal/cheburcheck` unit tests с локальным HTTP server |
| Пакетный use case, ранние результаты, отмена, глобальное ограничение темпа, cache TTL и Probe ID | `internal/blockcheck` unit tests и `internal/storage` SQLite tests |
| Создание/удаление серверов и правил, интервал пользователя, фильтрация по пользователю | `internal/monitor` unit tests |
| Первый статус, отсутствие повтора, недоступность → Cheburcheck → уведомление, восстановление | `internal/monitor` state-transition tests |
| Серверы и алерты доступны после переоткрытия SQLite | `internal/app` integration test с временной реальной SQLite |
| Сборка бота из конфигурации, доступность Compose-команды `serve` | `internal/app` tests и `docker compose config` |

## Интеграционные контракты и тестовая изоляция

Telegram и Cheburcheck — внешние HTTP API. Функциональные и unit-тесты используют loopback HTTP servers/transport doubles и не требуют токенов или доступа в Интернет. Интеграционный тест использует временный SQLite-файл и реальные доменные адаптеры; пользовательские данные не читаются.

Данные серверов и алертов принадлежат SQLite. Удаление сервера удаляет связанные с ним правила. SSH в текущей версии не используется и не хранится.

# tg-net-bot

Telegram-бот для ручной проверки серверов и настройки пользовательских алертов. Сервер можно проверить без сохранения или добавить в список. Бот выполняет проверки ICMP/TCP/HTTP и обращается к Cheburcheck, если настроенная проверка алерта обнаруживает недоступность сервера. Сервер задаётся доменом, IPv4 или IPv6.

## Установка на сервер

```sh
sh -c "$(curl -fsSL https://raw.githubusercontent.com/theillarion/tg-net-bot/45daee7f74f3eb4ce15534f092f81aa0718590fe/install.sh)"
```

Команда загружает проверенную версию установщика по SHA коммита, чтобы CDN-кеш ветки `master` не отдал предыдущую версию сразу после обновления. Установщик спросит каталог установки; по умолчанию используется текущая папка (`.`). Нажми Enter, чтобы оставить её. Если выбрать существующий клон, скрипт обновит его через fast-forward без перезаписи локальных изменений. Он запросит токен бота, разрешённые ID пользователей Telegram и необязательный прокси только при создании или замене `.env`; существующую конфигурацию можно сохранить и продолжить обновление. Если найдёт контейнер `tg-net-bot` от старой версии или предыдущий `tg-net-tools-bot`, спросит разрешение удалить его. Новая установка создаёт контейнер `tg-net-tools-bot`. Запускай установщик из пустой папки или из уже клонированного репозитория. Чтобы использовать форк, укажи `REPO_URL`.

## Запуск из клона репозитория

```sh
git clone https://github.com/theillarion/tg-net-bot.git
cd tg-net-bot
cp .env.example .env
# Укажи TELEGRAM_TOKEN и TALAGRAM_ALLOW_USERS в .env
docker compose up -d --build
```

Переменная `TALAGRAM_ALLOW_USERS` намеренно написана именно так, как было запрошено. Укажи через запятую числовые ID пользователей Telegram. Узнать свой ID можно с помощью Telegram-бота для просмотра ID; разрешай доступ только нужным аккаунтам. В `TELEGRAM_PROXY` можно указать HTTP(S)- или SOCKS5-прокси, например `socks5://host:port`. Compose использует host networking для доступа к локальному прокси. SQLite по-прежнему хранит серверы, алерты и незавершённые диалоги. Краткоживущий контекст Cheburcheck хранится в локальном Redis без персистентного диска; Redis слушает только loopback и не публикует порт.

## Локальный запуск CLI

В бинарном файле есть команды для ручных проверок и запуска бота:

```sh
go run ./cmd/tg-net-bot check --method tcp --arg 443 example.com
go run ./cmd/tg-net-bot check --method icmp 2001:db8::1
go run ./cmd/tg-net-bot block example.com another.example --output json
go run ./cmd/tg-net-bot block probe <cache-key>
go run ./cmd/tg-net-bot block example.com --redis-url 127.0.0.1:6379
go run ./cmd/tg-net-bot serve
```

Команда `check` выводит JSON в stdout — его можно передать, например, в `jq`. `block` принимает одну или несколько целей и поддерживает `text`, `json` и `ndjson`. Команда `block probe <cache-key>` вручную запускает расширенную проверку по сохранённому результату. Обе команды используют общий Redis из `REDIS_ADDR` (по умолчанию `127.0.0.1:6379`); `--redis-url` переопределяет адрес. Срок хранения задаётся `BLOCKCHECK_CACHE_TTL` (по умолчанию 24 часа), а `--cache-ttl` переопределяет максимум для CLI. Непроверенный JWT `exp` от Cheburcheck ограничивает срок cache и probe; для ID без корректного `exp` используется максимум 3 часа. Этот claim используется только как верхняя граница локального срока. Неиспользуемая таблица старого cache может оставаться в SQLite; новые записи туда не выполняются. Текущие defaults upstream — 30 check/мин и 5 probe/мин, burst 1; настройки production могут отличаться. Команда `serve` использует те же Redis-настройки. Справка по командам: `go run ./cmd/tg-net-bot --help`.

## Структура проекта

```text
cmd/tg-net-bot/       точка входа CLI и регистрация команд
internal/app/         сборка приложения и управление его жизненным циклом
internal/config/      загрузка и проверка настроек из окружения
internal/domain/      типы серверов и алертов
internal/monitor/     сценарии работы с серверами и алертами
internal/checker/     проверки доступности ICMP, TCP и HTTP
internal/blockcheck/  typed use case блокировок, batch, лимиты и cache port
internal/cheburcheck/ HTTP/SSE-клиент Cheburcheck
internal/storage/     SQLite-репозиторий и схема базы данных
internal/telegram/    адаптер Telegram Bot API и обработчики бота
```

Telegram и CLI используют общий `internal/blockcheck` use case; Cheburcheck остаётся адаптером данных, а форматирование вынесено в драйверы. Batch выполняется последовательно и передаёт результаты по мере готовности. В `internal/app` конкретные адаптеры связываются через конструкторы.

## Интерфейс Telegram-бота

После команды `/start` бот показывает постоянное меню с кнопками. Через него можно запускать разовые проверки доступности и Cheburcheck, управлять серверами и настраивать алерты — команды запоминать не нужно. Мастер настройки алерта предложит выбрать сервер, метод проверки, при необходимости порт или протокол, а затем периодичность, которую задаёт пользователь. У сохранённых серверов и алертов есть встроенные кнопки действий.

### Команды (необязательно)

- `/start` — открыть меню и показать справку.
- `/check <сервер> [icmp|tcp|http] [порт-или-URL]` — проверить сервер без сохранения или обратиться к сохранённому серверу по имени. Сервер можно указать по IP или домену. Для TCP по умолчанию используется порт 443; для HTTP — `https://<сервер>`.
- `/block <сервер>` — вручную проверить базовые списки Cheburcheck, независимо от того, сохранён сервер или нет. Можно указать IP или домен. Расширенный probe доступен отдельной кнопкой результата.
- `/add <имя> <IP-или-домен>` — сохранить сервер. Если отправить просто `/add`, бот проведёт через добавление пошагово.
- `/hosts` — показать сохранённые серверы.
- `/remove <имя>` — удалить сервер.
- `/alert <имя> <icmp|tcp|http> <интервал> [порт-или-URL]` — создать алерт для сохранённого сервера. Например: `/alert edge tcp 5m 443`. Когда проверка обнаружит переход в состояние «недоступен», бот запросит только базовый результат Cheburcheck и отправит уведомление. Тяжёлый probe не запускается автоматически. При восстановлении сервера бот сообщит об изменении состояния.
- `/alerts` — показать правила алертов.
- `/alert_remove <ID-правила>` — удалить правило алерта.

Для интервалов используется формат Go duration: `30s`, `5m`, `2h`. Пользователь задаёт интервал отдельно для каждого алерта в Telegram; общей настройки частоты проверок нет. Уведомления отправляются при переходе между состояниями. Первая успешная проверка только задаёт исходное состояние и не вызывает уведомление. У каждого правила свои метод и периодичность, а также необязательный порт или URL. Несохранённые серверы тоже можно проверять вручную. Данные SSH-доступа бот не запрашивает и не хранит.

Для ICMP в Compose добавлено разрешение `NET_RAW`; при этом удалённая сеть может блокировать ping. Проверка TCP устанавливает, принимает ли порт подключения. Проверка HTTP выполняет GET-запрос: коды ответа ниже 500 считаются доступными. Cheburcheck вызывается только после неудачной проверки, заданной в правиле алерта.

Серверы, отдельные интервалы алертов, последнее известное состояние и незавершённые шаги Telegram-форм хранятся в SQLite. Незавершённую форму можно продолжить после перезапуска бота; некорректный ввод не удаляет её состояние. По умолчанию база находится в `./data/tg-net-bot.sqlite`. Чтобы сохранить настройки и правила, делай резервную копию каталога `data/`.

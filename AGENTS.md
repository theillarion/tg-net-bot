# tg-net-bot

Telegram-бот для ручной проверки доступности серверов и пользовательских алертов. Источник состояния — SQLite. Для проверки доступны ICMP, TCP и HTTP(S); при переходе настроенного алерта в состояние «недоступен» бот дополнительно запрашивает Cheburcheck и отправляет уведомление. Пользователь сам задаёт для каждого алерта сервер, метод и интервал. Сервер можно указывать по домену, IPv4 или IPv6. SSH пока не используется.

## Команды

| Команда | Зачем |
| --- | --- |
| `make test-unit` | unit-тесты без внешних сервисов |
| `make test-functional` | сценарии пользователя через Telegram Bot API на локальном HTTP-моке |
| `make test-integration` | монитор + временная SQLite-база |
| `make coverage` | все уровни тестов и проверка общего покрытия ≥95% |
| `go test -race -tags=integration,functional ./...` | проверка гонок в полном наборе |
| `go vet ./...` | статический анализ Go |
| `docker compose config --quiet` | проверка Compose-конфигурации; для запуска команды должен существовать `.env` |

## Границы проекта

Никогда:
- не обращаться тестами или без явной команды к реальным серверам пользователя, Telegram Bot API или Cheburcheck; внешние HTTP-контракты проверять локальными моками;
- не читать, не выводить и не менять `.env`, SQLite-файлы в `data/`, токены и реальные пользовательские серверы;
- не заменять SQLite файловой сериализацией или in-memory хранилищем в рабочем приложении;
- не добавлять глобальный интервал алертов или настройки частоты через env: интервал задаётся отдельно пользователем в боте;
- не добавлять SSH-секреты/ключи до отдельного требования;
- не переписывать историю, не force-push и не публиковать релиз без явной команды.

Спросить до:
- добавления внешних зависимостей;
- несовместимого изменения схемы SQLite или пользовательского сценария;
- выполнения реальных сетевых проверок вне локальных тестовых серверов.

## Агенты

Для крупных изменений используй роли последовательно: `planner → implementer → tester → verifier`. Малые изменения могут идти напрямую в реализацию с независимой проверкой. Не запускай тестера, если для изменения нет исполняемых проверок. Каждый тест должен подтверждать наблюдаемое требование, пользовательский сценарий или содержательный отказ интеграции; тесты только ради покрытия строк запрещены.

### Роли

| Роль | Файл | Вход | Выход |
| --- | --- | --- | --- |
| planner | `docs/agents/planner/ROLE.md` | запрос, критерии приёмки | `.agents-cache/<task>/spec.md`, `hypotheses.md` |
| implementer | `docs/agents/implementer/ROLE.md` | `spec.md`, `hypotheses.md` | изменения, `claims.md` |
| tester | `docs/agents/tester/ROLE.md` | критерии, гипотезы, diff | результаты проверок |
| verifier | `docs/agents/verifier/ROLE.md` | spec, claims, diff | `verdicts.md`, PASS/FAIL |

### Артефакты

| Файл | Автор | Читатели |
| --- | --- | --- |
| `.agents-cache/<task>/spec.md` | planner | implementer, tester, verifier |
| `.agents-cache/<task>/hypotheses.md` | planner, verifier | implementer, tester, verifier |
| `.agents-cache/<task>/claims.md` | implementer | verifier |
| `.agents-cache/<task>/verdicts.md` | verifier | implementer, владелец |

## Тестовые сценарии

Критические пользовательские потоки описаны в `docs/architecture.md`. Для каждого изменения добавляй проверки на соответствующий поток: запуск/настройка, allowlist, ручная проверка без сохранения и сохранённого сервера, методы ICMP/TCP/HTTP, блокировка через Cheburcheck при недоступности, настройка и удаление алерта, переходы состояний и восстановление, сохранение после перезапуска.

Общее покрытие из `make coverage` должно оставаться не ниже 95%. Процент — сигнал о пропущенных сценариях, а не цель для искусственного исполнения веток. Не тестируй внутренние детали, если ту же гарантию можно проверить через внешний результат. Unit-тесты изолируют доменную логику; функциональные используют локальный HTTP-мок Bot API; интеграционные работают с временной SQLite и локальными сетевыми ресурсами.

## Соглашения

- Документация — на русском; сообщения кода и логи — на английском.
- Сохраняй границы: тонкие команды в `cmd/`, логика в `internal/`; интерфейсы объявляй рядом с потребителем, реализации связывай в `internal/app`.
- Новое поведение покрывай тестом основного сценария и значимыми отказами (недоступный внешний API, ошибка SQLite, отмена контекста), когда они меняют наблюдаемый результат.
- Сначала запускай узкие проверки, затем `make test-unit`, функциональные/интеграционные тесты и `make coverage`.
- Перед итогом проверь `git diff --check`, отсутствие секретов и случайных файлов.

## Чек-лист

| Проверка | Команда | Успех |
| --- | --- | --- |
| unit | `make test-unit` | все пакеты проходят |
| функциональные сценарии | `make test-functional` | основные действия в боте подтверждены через локальный Bot API |
| интеграция | `make test-integration` | данные переживают закрытие/повторное открытие SQLite |
| покрытие | `make coverage` | общий показатель ≥95% и проверки сценариев осмысленны |
| гонки | `go test -race -tags=integration,functional ./...` | exit 0 |
| статический анализ | `go vet ./...` | exit 0 |
| Compose | `docker compose config --quiet` | exit 0 с настроенным `.env` |
| diff | `git diff --check` | нет ошибок пробелов и конфликтных маркеров |
